Agentes de IA que pueden continuar después de fallar.

Cómo diseñar idempotencia, persistencia, reintentos y recuperación usando software abierto, sin confundir “volver a ejecutar” con “ejecutar sin duplicar efectos”.

Respuesta técnica: sí, con condiciones.

Las bibliotecas gratuitas proporcionan primitivas de ejecución duradera y colas, pero ninguna combinación garantiza automáticamente exactamente una ejecución de efectos externos. Hace falta identidad de tarea, base de datos duradera, deduplicación de operaciones, límites de reintentos y pruebas de interrupción. “Continuar” tampoco significa conservar memoria interna de una sesión LLM no registrada: hay que persistir entradas, decisiones, pasos y resultados.

1 · El patrón de referencia

Solicitud con ID→Cola duradera→Paso→Checkpoint→Fallo→Reinicio→Reintento seguro→Verificación

Idempotencia

Para la misma operación lógica, repetir una petición no debe duplicar el efecto empresarial. Use clave estable por operación, índice único y resultado persistido. Reutilice la misma clave en la API externa cuando lo admita.

Persistencia

Registre solicitud, identificador de flujo, versión, estado, pasos finalizados, salidas y errores en almacenamiento duradero. No dependa de memoria RAM ni exclusivamente de cachés.

Reintentos

Reintente únicamente errores transitorios, con backoff exponencial, jitter, límite de intentos y fecha máxima. No reintente sin control errores de permisos, validación o solicitudes mal construidas.

Recuperación

En el arranque, recupere operaciones pendientes, verifique efectos inciertos y continúe desde el último checkpoint confirmado. Aísle tareas que agotaron reintentos para revisión humana.

2 · Ruta mínima recomendada (Python)

Costos: software abierto; infraestructura aparte

DBOS + PostgreSQL

DBOS administra estado de workflows y checkpoints; PostgreSQL conserva el registro después de reinicios. Para un proyecto pequeño no es obligatorio sumar Celery: DBOS dispone de mecanismos de orquestación y colas propios. Añádalo solo cuando se justifique por integración o necesidades operativas.

  1. Instale PostgreSQL y establezca respaldos automáticos, retención y restauración ensayada.
  2. Instale DBOS; el ejemplo inicial usa pip install dbos. Configure DBOS_SYSTEM_DATABASE_URL con un usuario de mínimos privilegios.
  3. Defina un workflow_id único y estable a partir del identificador de la solicitud. Rechace nuevas solicitudes incompatibles con el mismo ID.
  4. Divida las acciones externas en steps; conserve entradas y resultados serializables.
  5. Para cada efecto externo, use una clave idempotente y un ledger propio; en respuestas ambiguas consulte el estado remoto antes de repetir.
  6. Configure reintentos solo para errores transitorios; marque como terminal un error funcional no recuperable.
  7. Reinicie el proceso a mitad de un workflow y verifique que continúa desde el último paso confirmado.

3 · Receta de claves idempotentes

Los IDs son del negocio, no números aleatorios nuevos en cada reintento. Esta operación SQL es una plantilla conceptual PostgreSQL, no una aplicación ejecutable completa:

CREATE TABLE operation_ledger (
  operation_key TEXT PRIMARY KEY,
  request_hash TEXT NOT NULL,
  status TEXT NOT NULL CHECK
    (status IN ('pending','running','done','failed','needs_review')),
  result_json JSONB,
  attempts INT NOT NULL DEFAULT 0,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- Para cada solicitud:
-- 1. INSERT ... ON CONFLICT DO NOTHING
-- 2. Si existe, comparar request_hash (conflicto = error).
-- 3. Bloquear/adquirir la operación de forma transaccional.
-- 4. Si status='done', reutilizar result_json.
-- 5. Si hay efecto remoto ambiguo, consultar el sistema remoto.
-- 6. Guardar resultado y estado final antes de responder.
Regla fundamental

Un índice único evita dos entradas para la misma clave, pero no evita por sí solo dos pagos, correos o llamadas externas. Combine ledger, exclusión de ejecuciones simultáneas, idempotency keys del proveedor y conciliación del resultado remoto. Cuando el servicio externo no soporte deduplicación, adopte compensación o revisión humana ante estados inciertos.

4 · Política operativa de reintentos

IncidenciaAcciónRazón
Timeout, HTTP 502/503/504Máx. 4 intentos, backoff exponencial y jitterFallo normalmente transitorio; verificar primero si el efecto se completó
HTTP 429Respetar Retry-After y aplicar límite globalEvitar saturar el servicio
HTTP 400/401/403 o datos inválidosNo reintentar automáticamenteRequiere corrección, credenciales o intervención
Proceso termina / host reiniciaRecargar checkpoints persistidosEl reinicio no debe borrar el estado
Respuesta ambigua de API externaConciliar por ID antes de repetirEl proveedor quizá procesó la acción
Intentos agotadosEstado needs_review y alertaEvitar bucles y pérdidas silenciosas

Ejemplo de parámetros iniciales: 4 intentos, espera base de 2 s, factor 2, jitter aleatorio limitado, tiempo máximo por operación de 15 min. Son valores orientativos y deben adaptarse a límites, latencias y semántica del proveedor.

6 · Sesiones LLM: qué persistir

Persistir solamente la cola no reconstruye una tarea de IA. Guarde: workflow_id, modelo y versión, instrucciones vigentes, referencias de documentos, mensajes necesarios, decisiones aceptadas, IDs de llamadas a herramientas, resultados, hashes de entradas, presupuesto de consumo y estado de aprobación humana. Al reanudar, reconstruya el contexto con esos datos y ejecute únicamente los pasos pendientes. No guarde secretos en texto plano ni asuma que una respuesta regenerada será idéntica.

7 · Pruebas de resiliencia antes de producción

  1. Duplicado: envíe la misma solicitud 10 veces simultáneamente. Debe existir una sola operación lógica y, en lo posible, un solo efecto remoto.
  2. Caída: mate el proceso después de una operación externa y antes de guardar la respuesta. Al reiniciar, verificar antes de reintentar.
  3. Reinicio: reinicie el worker a mitad de un flujo y asegure la recuperación del checkpoint.
  4. Fallo transitorio: simule 503/429; compruebe límites, Retry-After, jitter y máximo de intentos.
  5. Fallo permanente: simule 401 o validación fallida; debe detenerse, registrar la causa y permitir intervención.
  6. Base de datos: desconecte PostgreSQL; no se deben reportar finalizaciones sin confirmación persistida.
  7. Pérdida de ACK: fuerce la entrega repetida del mensaje; el consumidor debe tratar el duplicado como seguro.
  8. Restauración: restaure respaldos en entorno alterno y mida pérdida máxima de datos y tiempo de recuperación.
  9. Revisión: cada operación pendiente debe tener propietario, estado visible y procedimiento de conciliación.

8 · Costo y alcance de las garantías

Prototipo

DBOS + SQLite

Permite aprender y validar recuperación local sin pagar licencias del motor. No representa una configuración de alta disponibilidad ni reemplaza respaldos.

Producción pequeña

DBOS + PostgreSQL

Ruta simple con persistencia y workflows duraderos. Software de código abierto; el hosting, cómputo, almacenamiento, monitoreo y llamadas a modelos pueden generar costos.

Para alta disponibilidad multinstancia se requiere diseñar además la coordinación y recuperación distribuida. El plano de control DBOS Conductor puede tener licencias y costos distintos de la biblioteca abierta; su versión autoalojada está documentada con licencia propietaria. No es correcto afirmar que todas las piezas sean gratuitas en cualquier despliegue.

9 · Fuentes para verificar antes de implementar

  • DBOS: garantías de workflows y steps y retries.
  • DBOS: licenciamiento de Conductor autoalojado.
  • Restate: services, virtual objects y workflows.
  • Celery: task acknowledgments e idempotencia.
  • NATS JetStream: deduplicación y acknowledgements.
  • Trigger.dev: retries e idempotencia.

Criterio de aceptación

Un agente es recuperable cuando una solicitud repetida no duplica el efecto empresarial, un reinicio conserva el progreso, un error transitorio se reintenta dentro de límites, uno permanente se detiene y cada resultado puede auditarse. Una demostración sin pruebas de fallos es solamente un prototipo.
